# 6.1 이미지 빌드 및 업로드
## 6.1.1 이미지 태그
- 이미지의 이름을 변경하는 방법은 없지만, 태그 기능을 사용하여 이미지를 가리키는 이름을 추가할 수 있음
- 이미지 업로드 목적이라면 태그를 지정할 때, `허브 ID/저장소이름:태그` 형식으로 지정

```sh
vagrant@docker:~$ docker container run -itd --name before-con alpine:latest 
85d15edaed6a82ab58a0c58ce02418e8a5f658d0caa59f4585ca95cc7f489be4
# -itd : 터미널 연결 + interactive + 백그라운드(detached)
# --name before-con : 컨테이너 이름 지정
# alpine:latest 이미지로 컨테이너 생성 및 실행

vagrant@docker:~$ docker container exec before-con mkdir /before-dir
# 실행 중인 before-con 컨테이너 안에서 /before-dir 디렉토리 생성

vagrant@docker:~$ docker container exec before-con touch /before-file
# 실행 중인 before-con 컨테이너 안에 before-file 파일 생성

vagrant@docker:~$ docker container commit before-con
sha256:98923cd1b588f0ba08feced0b64b462a55ed533c7d4dacf603fbed06f1ca5306
# 현재 before-con 컨테이너의 상태를 새로운 이미지로 저장(commit)
# 이 commit 결과로 새로운 이미지 ID가 생성됨 (이름 없음)

vagrant@docker:~$ docker image ls
IMAGE              ID             DISK USAGE   CONTENT SIZE   EXTRA
alpine:latest      865b95f46d98       13.1MB         3.95MB    U 
...
# 기존 alpine 이미지만 보임 — commit 한 이미지는 아직 태그가 없음

vagrant@docker:~$ docker image ls
IMAGE              ID             DISK USAGE   CONTENT SIZE   EXTRA
alpine:latest      865b95f46d98       13.1MB         3.95MB    U 
new-img:latest     4b650274ef43         13MB         3.86MB
...
# new-img:latest 라는 이름으로 태그(tag) 붙인 이미지가 추가됨

vagrant@docker:~$ docker image prune
WARNING! This will remove all dangling images.
Are you sure you want to continue? [y/N] y
# 태그가 없는(=dangling) 이미지 삭제
# commit 후 태그 안 붙인 최초 상태의 이미지가 제거됨

Total reclaimed space: 1.497kB

vagrant@docker:~$ docker container run -it --rm new-img:latest
/ # ls
before-dir   bin          etc          lib          mnt          proc         run          srv          tmp          var
before-file  dev          home         media        opt          root         sbin         sys          usr
/ # exit
# new-img:latest 이미지로 컨테이너 실행
# --rm : 컨테이너 종료 시 자동 삭제
# ls 결과에 before-dir, before-file 이 존재 ⇒ commit한 내용이 이미지에 포함된 것 확인

vagrant@docker:~$ docker image ls
IMAGE              ID             DISK USAGE   CONTENT SIZE   EXTRA
alpine:latest      865b95f46d98       13.1MB         3.95MB    U 
new-img:latest     4b650274ef43         13MB         3.86MB
# alpine + 새로 만든 new-img 이미지가 남아 있음

```

# 6.2 Dockerfile
## 6.2.1 Dockerfile 개요
- Dockerfile은 코드 형태의 텍스트 문서이며, 여러 가지 지시어를 사용하여 이미지를 제작할 수 있음
- 버전 관리가 용이하고, 이미지의 기능을 파악하기 쉬움

## 6.2.2 Dockerfile 지시어

|지시어|설명|
|---|---|
|FROM|베이스 이미지 지정|
|RUN|이미지를 생성하면서 실행할 명령 지정|
|CMD|컨테이너의 어플리케이션 지정|
|ENTRYPOINT|컨테이너의 어플리케이션 지정|
|EXPOSE|컨테이너의 포트 지정|
|ENV|컨테이너의 환경 변수 지정|
|ADD|이미지 생성 시 파일 추가|
|COPY|이미지 생성 시 파일 복사|
|VOLUME|컨테이너의 볼륨 지정|
|USER|컨테이너의 사용자 지정|
|WORKDIR|컨테이너의 작업 디렉토리 지정|
- RUN, CMD, ENTRYPOINT 지시어들은 exec와 shell 형식으로 사용할 수 있음
- exec 형식은 쉘을 통해 실행하지 않으며, shell 형식은 /bin/sh와 같은 쉘을 통해 지정된 명령을 실행함



```sh
vagrant@docker:~$ docker image pull rockylinux:9
# rockylinux:9 이미지 다운로드

vagrant@docker:~$ vim Dockerfile
# Dockerfile을 vim 에디터로 생성/수정

vagrant@docker:~$ cat Dockerfile
FROM rockylinux:9
# Dockerfile 내용을 출력 (현재는 기본 이미지만 지정됨)

vagrant@docker:~$ docker image build -t new-img:v1 .
# 현재 디렉토리에 있는 Dockerfile로 새 이미지 생성
# 태그명: new-img:v1
# → Dockerfile이 FROM 뿐이라서 기본 rockylinux 이미지를 그대로 사용한 이미지가 만들어짐

vagrant@docker:~$ echo "FROM    rockylinux:9" > Dockerfile
# 기존 Dockerfile 내용을 덮어쓰고 FROM rockylinux:9 한 줄만 넣음

vagrant@docker:~$ echo "RUN    touch /test_dockerfile" >> Dockerfile
# Dockerfile 마지막 줄에 RUN touch 명령 추가
# /test_dockerfile 파일을 이미지 빌드 과정에서 미리 생성하게 됨

vagrant@docker:~$ cat Dockerfile
FROM    rockylinux:9
RUN    touch /test_dockerfile
# Dockerfile 두 줄 확인

vagrant@docker:~$ docker image build -t new-img:v2 .
# 새로운 Dockerfile로 이미지 생성
# 태그명: new-img:v2
# → 빌드 도중 /test_dockerfile 파일이 이미지 내부에 생성됨

docker container run -itd --name v1-con new-img:v1
# new-img:v1 이미지로 컨테이너 실행 (백그라운드)

docker container run -itd --name v2-con new-img:v2
# new-img:v2 이미지로 컨테이너 실행 (백그라운드)

docker container exec -t v1-con ls
# v1-con 컨테이너 내부 파일 목록 출력
# (여기엔 /test_dockerfile 없음)

docker container exec -t v2-con ls
# v2-con 컨테이너 내부 파일 목록 출력
# (여기에는 /test_dockerfile 파일이 존재함)
```
*rockylinux (이미지) -> docker run (컨테이너) -> 내부에서 touch 명령어 사용 -> commit 명령어로 이미지 저장*
*rockylinux (이미지) -> Dockerfile 작성 (FROM rockylinux:9) + RUN touch /textfile -> docker build (이미지 생성)*

```sh
vagrant@docker:~$ echo "EXPOSE 80/tcp" >> Dockerfile
# Dockerfile 마지막 줄에 'EXPOSE 80/tcp' 추가
# → 이미지가 80번 포트를 사용한다는 “메타데이터”를 Docker에 알려줌 (자동 포워딩 아님!)

vagrant@docker:~$ docker image build -t new-img:v3 .
# EXPOSE가 포함된 Dockerfile로 이미지 생성 → new-img:v3

vagrant@docker:~$ docker image inspect new-img:v3
# 이미지 메타데이터 확인
# → Config.ExposedPorts 항목에 "80/tcp": {} 가 추가됨

vagrant@docker:~$ echo "ENV    MYVARS=123" >> Dockerfile
# Dockerfile에 환경 변수 MYVARS=123 추가
# 이미지 안에 기본 환경값으로 저장됨

vagrant@docker:~$ docker image build -t new-img:v4 .
# 환경변수가 추가된 Dockerfile로 이미지 빌드 → new-img:v4

vagrant@docker:~$ docker image inspect new-img:v4
# Inspect에서 Config.Env 항목에 MYVARS=123 포함됨

vagrant@docker:~$ touch add_file copy_file
# ADD와 COPY 테스트를 위해 빈 파일 두 개 생성

vagrant@docker:~$ echo "ADD    add_file /mnt" >> Dockerfile
# add_file을 이미지 빌드 시 /mnt 경로로 복사
# ADD는 tar 자동 압축 해제 기능도 있지만 여기서는 단순 복사

vagrant@docker:~$ echo "COPY   copy_file /mnt" >> Dockerfile
# copy_file 파일도 이미지 빌드 시 /mnt로 복사

vagrant@docker:~$ docker image build -t new-img:v5 .
# ADD, COPY가 적용된 이미지 생성 → new-img:v5

vagrant@docker:~$ docker image inspect new-img:v5
# ADD/COPY로 복사된 파일들이 레이어에 반영되었는지 확인

vagrant@docker:~$ docker container run --rm new-img:v5 ls /mnt
add_file
copy_file
# 복사된 파일들이 정상적으로 /mnt 에 존재함

vagrant@docker:~$ echo "VOLUME /mnt" >> Dockerfile
# /mnt를 볼륨 마운트 지점으로 설정
# → 컨테이너 실행 시 익명 볼륨이 자동 연결됨
# → /mnt의 내용은 호스트의 /var/lib/docker/volumes/ 아래에 저장됨

vagrant@docker:~$ docker image build -t new-img:v6 .
# Volume 설정이 포함된 이미지 생성 → new-img:v6

vagrant@docker:~$ docker image inspect new-img:v6
# Config.Volumes 항목에 "/mnt": {} 추가 확인
```

### 명령어 입력 방식
  ls  -l  /etc
  EN  CMD
  docker-entrypoint.sh  mysqld

- CMD만 있을 경우
docker container run xxxxxxxx IMAGE
  -> IMAGE에서 설정해둔 CMD
docker container run xxxxxxxx IMAGE ls
  -> IMAGE에서 설정해둔 CMD 대신 ls 명령어 실행
- Entry Point만 있을 경우
docker container run xxxxxxxx IMAGE
  -> IMAGE에서 설정해둔 ENTRYPOINT만 인자값 없이 실행
docker container run xxxxxxxx IMAGE ls
  -> IMAGE에서 설정해둔 ENTRYPOINT에 ls라는 인자값을 전달해서 실행

```sh
vagrant@docker:~$ echo "CMD   ls" >> Dockerfile     # Dockerfile 끝에 CMD ls 추가 (기본 실행 명령어)
vagrant@docker:~$ docker image build -t new-img:v10 .   # v10 이미지 빌드
vagrant@docker:~$ docker image inspect new-img:v10       # 이미지 정보 확인 (CMD가 ls로 들어있음)

vagrant@docker:~$ vim Dockerfile                        # Dockerfile 내용 수정
FROM    rockylinux:9                                    # 베이스 이미지: Rocky Linux
RUN     touch /test_dockerfile                          # 파일 생성
EXPOSE 80/tcp                                           # 80 포트 노출
ENV     MYVARS=123                                      # 환경변수 설정
ADD    add_file /mnt                                    # add_file 을 /mnt 에 추가
COPY   copy_file /mnt                                   # copy_file 을 /mnt 에 복사
VOLUME /mnt                                             # /mnt 를 볼륨으로 지정
RUN    useradd myuser                                   # myuser 사용자 추가
USER    myuser                                          # 기본 사용자 변경 (myuser로 실행)
ENTRYPOINT   ls                                         # ENTRYPOINT 지정 → 무조건 ls 실행됨

vagrant@docker:~$ docker image build -t new-img:v11 .   # ENTRYPOINT가 적용된 v11 이미지 빌드

vagrant@docker:~$ docker container run --rm -it new-img:v11 
afs  bin  dev  etc  home ...                            # ENTRYPOINT ls 실행 → ls 출력됨

vagrant@docker:~$ docker container run --rm -it new-img:v11 bash
afs  bin  dev  etc  home ...                            # bash 요청했지만 ENTRYPOINT(ls)가 우선이라 ls가 실행됨
# 즉: ENTRYPOINT는 사용자가 명령을 줘도 무조건 실행된다

vagrant@docker:~$ docker container run --rm -it new-img:v11 pwd
afs  bin  dev  etc  home ...                            # pwd 요청해도 ENTRYPOINT ls 실행됨
# ENTRYPOINT = ls
```

#### 개발 작업 순서
```
1. 온프레미스에서 직접 개발 및 배포
  1) 편집기로 소스 코드 작성
  2) 빌드 도구 설치
  3) 코드를 실행 파일로 변환 (빌드 / 컴파일)
  4) 실행 파일을 배포 (운영 서버로 이동)
  5) 실행 (운영 서버에서)
2. 도커에서 개발 및 배포
  1) 편집기로 소스 코드 작성  -> 동일
  2) 빌드 도구가 설치되어 있는 이미지로 컨테이너 실행
  3) 해당 컨테이너에 소스 코드를 복사
  4) 컨테이너 내부에서 빌드 명령어 실행
  5) 생성된 실행 파일을 호스트로 복사
  6) 실행 파일을 사용해서 이미지를 생성
  7) 생성한 이미지로 배포 (컨테이너 실행)
```
