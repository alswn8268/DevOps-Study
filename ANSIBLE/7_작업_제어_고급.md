# 7.1 작업 오류 처리
- `ansible`은 작업 중에 오류를 수신하면 해당 호스트에서 해당 작업 및 후속 작업을 중지하고, 다른 호스트가 있다면 다른 호스트에서 작업을 계속 실행함.
- 그러나 경우에 따라 오류를 다른 방법으로 처리하고 싶을 수 있고, 드물게 정상적인 상황일 수 있음
```bash
- name: task2
ansible.builtin.command: error
ignore_errors: true


TASK [task2] ******************************************************************************************************************************************************************************
fatal: [localhost]: FAILED! => {"changed": false, "cmd": "error", "msg": "[Errno 2] No such file or directory: b'error'", "rc": 2, "stderr": "", "stderr_lines": [], "stdout": "", "stdout_lines": []}
...ignoring
```

## 7.1.1. 실패한 명령 무시
- `ignore_errors` 키워드는 리턴 코드가 0이 아닌 경우에만 작동하며, `변수 오류`, `연결 실패`, `실행 문제`, `구문 오류`는 무시하지 않음

## 7.1.2 연결할 수 없는 호스트 무시
- `unreachable` 상태인 경우 `ignore_unreachable` 키워드로 작업 실패를 무시할 수 있음.
- 후속 작업은 해당 관리 노드에서 계속 실행됨

```tasks
- name: Block Test Playbook
  hosts: error-server
  gather_facts: false
  tasks:
    - name: Block Name
      block:
        - name: task1
          ansible.builtin.debug:
            msg: before error

        - name: task2
          ansible.builtin.command: error
          ignore_errors: true
...


TASK [task1] ******************************************************************************************************************************************************************************
ok: [servera] => {
    "msg": "before error"
}
TASK [task2] ******************************************************************************************************************************************************************************
fatal: [servera]: UNREACHABLE! => {"changed": false, "msg": "Failed to connect to the host via ssh: ssh: Could not resolve hostname servera: Name or service not known", "unreachable": true}


- name: Block Test Playbook
  hosts: error-server
  gather_facts: false
  tasks:
    - name: Block Name
      block:
        - name: task1
          ansible.builtin.command: id
          ignore_unreachable: true
        - name: task2
          ansible.builtin.command: error
          ignore_errors: true

TASK [task1] ******************************************************************************************************************************************************************************
fatal: [servera]: UNREACHABLE! => {"changed": false, "msg": "Failed to connect to the host via ssh: ssh: Could not resolve hostname servera: Name or service not known", "unreachable": true}
...ignoring

TASK [task2] ******************************************************************************************************************************************************************************
fatal: [servera]: UNREACHABLE! => {"changed": false, "msg": "Failed to connect to the host via ssh: ssh: Could not resolve hostname servera: Name or service not known", "unreachable": true}
```

## 7.1.3 핸들러의 실패
- 작업이 변경되어 알림을 보내더라도 후속 작업이 오류가 발생해 핸들러가 실행되지 않을 수가 있는데, 이런 경우 핸들러를 강제로 실행할 수 있음

```
---
- name: Test Handler
  hosts: nodes
  become: true
  force_handlers: true
  tasks:
    - name: Apache Package Install
      ansible.builtin.yum:
        name: mod_ssl
        state: latest
      notify:
        - Restart apache
    - command: error
  handlers:
    - name: Resetart apache
      ansible.builtin.service:
        name: httpd
...      
```

## 7.1.4 실패 재정의
- `ansible`은 명령 모듈의 리턴코드가 0이거나, 작업의 오류가 발생할 때 실패를 보고함
- 그러나 작업 실패에 대한 의미를 `failed_when` 키워드로 재정의할 수 있음
- `failed_when`은 조건문으로 선언함


## 7.1.5 변경 재정의
- `ansible`은 작업의 변경 상태에 대한 조건을 `changed_when` 키워드로 재정의할 수 있음 -> 핸들러를 트리거하기 위함

``` bash
---
- name: Test Handler
  hosts: nodes
  become: true
  force_handlers: true
  tasks:
    - name: Apache Package Install
      ansible.builtin.yum:
        name: php
        state: latest
      changed_when: true
      notify:
        - Restart apache
    - command: error
      failed_when: false
  handlers:
    - name: Restart apache
      ansible.builtin.service:
        name: httpd
        state: restarted
...


TASK [Apache Package Install] *************************************************************************************************************************************************************
changed: [192.168.56.202]
changed: [192.168.56.201]

TASK [command] ****************************************************************************************************************************************************************************
ok: [192.168.56.202]
ok: [192.168.56.201]

RUNNING HANDLER [Restart apache] **********************************************************************************************************************************************************
changed: [192.168.56.202]
changed: [192.168.56.201]
```

## 7.1.6 command 및 shell 모듈 작업의 성공 보장
- `/bin/true` 명령을 사용하며 command 모듈 및 shell 모듈 실행 시 항상 리턴 코드를 0으로 하여 작업의 성공을 보장할 수 있음


## 7.1.7 모든 호스트 작업 중단
- 경우에 따라 일부 호스트 작업의 오류가 발생한 경우 모든 호스트에 대해 작업 실행을 중단할 수 있음

```bash
[vagrant@ansible-controller second]$ ssh vagrant@192.168.56.201
[vagrant@ansible-node1 ~]$ sudo yum install -y php
[vagrant@ansible-node1 ~]$ exit

[vagrant@ansible-controller second]$ ssh vagrant@192.168.56.202
[vagrant@ansible-node2 ~]$ sudo yum remove -y php
[vagrant@ansible-node2 ~]$ exit

[vagrant@ansible-controller second]$ vi any_error.yaml

---
- name: Test any_error_fatal option
  hosts: nodes
  tasks:
    - name: normal command
      command: id
    - name: php command
      command: php -v
    - name: normal command
      command: id
...

[vagrant@ansible-controller second]$ ansible-playbook any_error.yaml

TASK [normal command] *********************************************************************************************************************************************************************

changed: [192.168.56.201]

TASK [php command] ************************************************************************************************************************************************************************

changed: [192.168.56.201]

TASK [normal command] *********************************************************************************************************************************************************************
```

### 7.1.7.1 첫 번째 오류에서 중단
- `any_errors_fatal` 키워드를 사용하면 작업 실패 시 모든 호스트의 작업이 중단됨

### 7.1.7.2 최대 실패율 설정
- 작업이 실패하지 않는 호스트가 있는 경우, 해당 호스트의 작업을 계속 진행하도록 하는 설정도 가능함

# 7.2 전략 및 롤링 업데이트
- `ansible`은 기본적으로 5개의 `포크(Fork)`를 사용해 하나의 작업을 동시에 5개의 호스트에서 실행함
- `serial` 키워드를 사용해서 `ansible`이 플레이를 한 번에 실행해야 하는 호스트의 수를 제한할 수 있음

```bash
[vagrant@ansible-controller second]$ vi test.sh

#!/bin/bash
sleep 10
```

# 7.3 비동기 
- `ansible`은 기본적으로 `동기식(Synchronous)`으로 작업이 완료될 때까지 호스트에 대한 연결을 열어두고, 작업 완료까지 후속 작업을 실행하지 않음
- 이런 동기식 방식은 SSH 세션에 문제를 야기할 수 있기 때문에 `비동기식(Asychronous)` 방식을 사용해 이를 해결할 수 있음

```
# 동기
[vagrant@ansible-controller second]$ ssh vagrant@192.168.56.201
Last login: Wed Nov 26 07:08:04 2025 from 192.168.56.200
[vagrant@ansible-node1 ~]$ mkdir /tmp/testdir
[vagrant@ansible-node1 ~]$ touch /tmp/fileA
[vagrant@ansible-node1 ~]$ exit
logout

# 비동기
[vagrant@ansible-controller second]$ ssh vagrant@192.168.56.201 mkdir /tmp/newdir
vagrant@192.168.56.201's password: 
[vagrant@ansible-controller second]$ ssh vagrant@192.168.56.201 touch /tmp/newfile
vagrant@192.168.56.201's password: 
```

# 7.4 태그
- 많은 작업이 있는 플레이북의 경우 ansible 태그로 특정 작업만 실행하거나, 특정 작업을 실행하지 않을 수 있음
- 태그는 블록, 플레이, 역할, 작업에 설정하고, 플레이북 실행 시 태그를 선택함

```bash
[vagrant@ansible-controller second]$ vi tag.yaml

---
- name: Test Playbook with tag
  hosts: localhost
  tasks:
    - debug:
        msg: "First Task"
      tags:
        - task1
    - debug:
        msg: "Second Task"
      tags:
        - task2
    - debug:
        msg: "Third Task"
    - debug:
        msg: "Fourth Task"
- hosts: localhost
  tasks:
    - debug:
        msg: "2-1 Task"
    - debug:
        msg: "2-2 Task"
...      

[vagrant@ansible-controller second]$ ansible-playbook tag.yaml --tags=task1,task2

[vagrant@ansible-controller second]$ ansible-playbook tag.yaml --skip-tags=play1
```
