vagrant@kube-control1:~/hpa$ vim myapp-rs-nn.yaml

# ReplicaSet을 특정 노드(kube-node1)에 스케줄링해서 3개의 Pod를 띄우는 설정
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: myapp-rs-nn # ReplicaSet 이름
spec:
  replicas: 3 # Pod 3개 만들기
  selector:
    matchLabels:
      app: myapp-rs-nn # 어떤 Pod를 관리할지 선택 기준
  template:
    metadata:
      labels:
        app: myapp-rs-nn
    spec:
      nodeName: kube-node1 # 스케줄러를 우회해서 Pod를 강제로 kube-node1에 배치 (하드 바인딩)
      containers:
        - name: myapp
          image: ghcr.io/nobreak-labs/go-myweb:alpine

vagrant@kube-control1:~/hpa$ kubectl create -f myapp-rs-nn.yaml

----
#### 파드 스케줄링
- 파드를 어떤 노드에 실행할지를 결정
- kube-scheduler가 해당 작업을 수행
- 노드들의 상태를 확인해서 처리 (kubelet 서비스가 담당)
- 각 노드의 리소스 사용량에 따라 처리
- 필요에 따라 별도의 스케줄링 기법 사용 가능
  1. `노드 네임`: 무조건 노드의 이름만 확인해서 강제 배치 (kube-scheduler와 무관)
  2. `노드 셀렉터`: 노드마다 레이블을 설정해두고, 파드를 생성할 때에 해당 레이블을 선택하도록 설정하는 방식 (강제)
  3. `노드 어피니티`: 노드 셀렉터처럼 레이블/셀렉터 기준으로 배치
    required 방식(강제)과 preferred(권장) 방식이 존재
  4. `파드 어피니티`: 파드의 레이블을 기준으로 같은 곳에 배치
  5. `파드 안티 어피니티`: 파드의 레이블을 기준으로 다른 곳에 배치
  6. `테인트`: 노드에 레이블처럼 키/값 형태로 설정해두는 항목
    해당 노드는 특수한 목적으로 판단하고 가급적 피해서 
  7. `톨러레이션`: 파드 생성 시 해당 테인트가 설정된 노드에도 배치를 허용
  8. `커든`: 무조건 해당 노드는 사용 불가 - 기존의 파드는 그대로 남겨두는 방식
  9. `드레인`: 무조건 해당 노드는 사용 불가 - 기존의 파드도 다 종료하는 방식
